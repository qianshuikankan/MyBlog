面向对象设计（Object-Oriented Design，OOD）是软件工程中一种重要的设计方法，它以对象为核心，通过类和对象的**封装、继承和多态**等特性来构建系统。为了设计出高质量、可维护、可扩展且易于理解的面向对象系统，通常遵循以下几种重要的设计原则：

# 1. **开闭原则（Open-Closed Principle，OCP）**
- **定义**：软件实体应该对扩展开放，对修改关闭。即在不修改已有代码的情况下，能够通过添加新的代码来实现功能的扩展。
- **意义**：遵循开闭原则可以减少系统因需求变更而带来的修改成本，增强系统的稳定性和可维护性。
- **实现方式**：通常通过抽象化和多态来实现。例如，定义一个抽象基类或接口，通过继承或实现接口来扩展功能，而无需修改原有代码。

**举例子：**

###  Java集合框架 - `Collections.sort()` 与 `Comparator`

这是最经典的例子。排序算法（封闭）不变，但比较规则（开放）可扩展：

```java
// JDK源码：排序算法完全封闭
public class Collections {
    public static <T> void sort(List<T> list, Comparator<? super T> c) {
        list.sort(c);  // 算法固定，比较逻辑外抛
    }
}

// Comparator接口：开放的扩展点
public interface Comparator<T> {
    int compare(T o1, T o2);  // 策略方法
}
```



```
import java.util.*;

// ========== 被排序的实体类（封闭，不需要修改） ==========
public class Student {
    private String name;
    private double score;
    private int age;
    

    public Student(String name, double score, int age) {
        this.name = name;
        this.score = score;
        this.age = age;
    }
    
    // 只有getter，无setter，值对象
    public String getName() { return name; }
    public double getScore() { return score; }
    public int getAge() { return age; }
    
    @Override
    public String toString() {
        return name + "(" + score + ")";
    }

}

// ========== 扩展点：各种具体的比较策略（开放） ==========

/**

 * 策略1：按成绩降序排列
 * 完全独立的具名类，不修改任何现有代码
   */
   public class ScoreDescendingComparator implements Comparator<Student> {
   @Override
   public int compare(Student s1, Student s2) {
       // 降序：后减前
       return Double.compare(s2.getScore(), s1.getScore());
   }
   }

/**

 * 策略2：按成绩升序排列
   */
   public class ScoreAscendingComparator implements Comparator<Student> {
   @Override
   public int compare(Student s1, Student s2) {
       return Double.compare(s1.getScore(), s2.getScore());
   }
   }

/**

 * 策略3：按姓名字典序排列
   */
   public class NameComparator implements Comparator<Student> {
   @Override
   public int compare(Student s1, Student s2) {
       return s1.getName().compareTo(s2.getName());
   }
   }

/**

 * 策略4：先按成绩降序，成绩相同按年龄升序
 * 组合策略，展示扩展的灵活性
   */
   public class ScoreThenAgeComparator implements Comparator<Student> {
   @Override
   public int compare(Student s1, Student s2) {
       int scoreCompare = Double.compare(s2.getScore(), s1.getScore());
       if (scoreCompare != 0) {
           return scoreCompare;
       }
       // 成绩相同，比较年龄
       return Integer.compare(s1.getAge(), s2.getAge());
   }
   }

// ========== 使用：动态注入不同策略 ==========
public class SortDemo {
    public static void main(String[] args) {
        List<Student> list = new ArrayList<>();
        list.add(new Student("张三", 85.5, 20));
        list.add(new Student("李四", 92.0, 21));
        list.add(new Student("王五", 85.5, 19));
        list.add(new Student("赵六", 78.0, 22));
        

        // 扩展1：按成绩降序
        Collections.sort(list, new ScoreDescendingComparator());
        System.out.println("成绩降序：" + list);
        // 输出：[李四(92.0), 张三(85.5), 王五(85.5), 赵六(78.0)]
        
        // 扩展2：按姓名排序（不修改Student类，不修改Collections）
        Collections.sort(list, new NameComparator());
        System.out.println("姓名排序：" + list);
        // 输出：[李四(92.0), 王五(85.5), 张三(85.5), 赵六(78.0)]
        
        // 扩展3：组合策略
        Collections.sort(list, new ScoreThenAgeComparator());
        System.out.println("成绩降序+年龄升序：" + list);
        // 输出：[李四(92.0), 王五(85.5), 张三(85.5), 赵六(78.0)]
        // 注意：张三和王五成绩相同，王五年龄小排前面
    }

}
```

**体现开闭原则**：排序算法（闭）固定，比较策略（开）可无限扩展。



# 2. **里氏替换原则（Liskov Substitution Principle，LSP）**

- **定义**：子类对象必须能够替换掉它们的父类对象，并且不破坏系统的正确性。即子类对象必须能够无缝地替换父类对象，而调用者无需感知到任何差异。
- **意义**：确保继承关系的合理性，避免因继承带来的问题，如子类行为与父类不一致。
- **实现方式**：子类必须完全实现父类的行为，并且不能改变父类原有的行为。例如，子类可以扩展父类的功能，但不能改变父类的已有功能。



```java
import java.util.List;
import java.util.ArrayList;
import java.util.LinkedList;

public class Demo {
    

    // 这个方法只关心 List 接口的契约，不关心具体实现
    public static int sum(List<Integer> numbers) {
        int total = 0;
        for (int num : numbers) {
            total += num;
        }
        return total;
    }
    
    // 这个方法也只依赖 List 接口
    public static void printAll(List<String> items) {
        for (int i = 0; i < items.size(); i++) {
            System.out.println(items.get(i));
        }
    }
    
    public static void main(String[] args) {
        // LSP 验证：ArrayList 可以无缝替换 List
        List<Integer> list1 = new ArrayList<>();
        list1.add(10);
        list1.add(20);
        list1.add(30);
        System.out.println("ArrayList求和: " + sum(list1));  // 输出 60
        
        // LSP 验证：LinkedList 也可以无缝替换 List
        List<Integer> list2 = new LinkedList<>();
        list2.add(1);
        list2.add(2);
        list2.add(3);
        System.out.println("LinkedList求和: " + sum(list2));  // 输出 6
        
        // 甚至可以中途替换，程序行为完全一致
        List<String> items;
        
        items = new ArrayList<>();
        items.add("ArrayList item");
        printAll(items);  // 正常工作
        
        items = new LinkedList<>();  // 替换为子类
        items.add("LinkedList item");
        printAll(items);  // 同样正常工作，行为完全一致
    }

}
```



# 3 单一职责原则（Single Responsibility Principle，SRP）
- **定义**：一个类应该只有一个发生变化的原因。如果一个类负责多个功能，那么当其中一个功能发生变化时，可能会导致其他功能受到影响。
- **意义**：降低类的复杂度，提高类的可读性和可维护性，同时减少类之间的耦合。
- **实现方式**：将类的功能拆分为多个单一职责的类。例如，一个类只负责数据的存储，另一个类负责数据的处理。

```
import java.util.List;
import java.util.ArrayList;
import java.util.Collections;

public class Demo {
    

    public static void main(String[] args) {
        List<Integer> list = new ArrayList<>();
        list.add(3);
        list.add(1);
        list.add(2);
        
        // Collections 类的职责：提供集合的通用算法操作
        // 它不负责存储数据，只负责"操作"集合
        
        Collections.sort(list);           // 职责：排序算法
        Collections.reverse(list);        // 职责：反转算法  
        Collections.shuffle(list);        // 职责：随机打乱
        Collections.binarySearch(list, 2); // 职责：查找算法
        
        // 注意：Collections 与 Collection 接口职责分离
        // Collection 接口：定义集合的基本操作契约（add/remove/size）
        // Collections 类：提供集合的算法工具（sort/search/shuffle）
    }

}
```



## 违背的例子：`Properties` 的问题

`java.util.Properties` 同时承担了**三个不同职责**：

### 1. 键值对存储（Map 的职责）
```java
Properties p = new Properties();
p.setProperty("db.url", "jdbc:mysql://localhost/test");
p.getProperty("db.url");
```
这是配置数据的容器功能，类似 `HashMap<String, String>`。

### 2. 字符串限定（类型约束的职责）
```java
// 键和值都必须是 String，不能是其他类型
p.put("key", 123);      // 编译通过但设计意图错误，实际应 put(Object,Object)
p.setProperty("key", "123");  // 正确用法
```
它继承自 `Hashtable<Object,Object>`，却自我限制为 `String` 键值，这种"假装是通用 Map 实际是专用 Map"的做法造成了职责混乱。

### 3. 文件 IO 操作（持久化的职责）
```java
// 加载配置文件
p.load(new FileInputStream("config.properties"));
// 保存到文件
p.store(new FileOutputStream("config.properties"), "comments");
```
包含了**文件读写、格式解析、注释处理**等 IO 相关逻辑。

---

## 职责冲突的表现

| 职责     | 变化原因                             | 影响                 |
| -------- | ------------------------------------ | -------------------- |
| 存储结构 | 需要改用 ConcurrentHashMap 实现      | 被迫连带修改 IO 代码 |
| 文件格式 | 需要支持 YAML/XML/JSON               | 存储逻辑也被牵扯     |
| 类型约束 | 需要支持非 String 值（如整数、列表） | IO 序列化逻辑需重写  |

---

## 符合 SRP 的设计应该这样拆分

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  Configuration  │────▶│  ConfigStorage  │◄────│  ConfigLoader   │
│   (业务接口)     │     │  (存储/查询接口)  │     │  (文件解析接口)   │
└─────────────────┘     └─────────────────┘     └─────────────────┘
        │                       │                       │
        ▼                       ▼                       ▼
   读取配置项               HashMap/TreeMap          PropertiesFileLoader
   设置默认值               DatabaseStorage          YamlLoader
   类型转换                 RedisStorage             JsonLoader
```

# 4. **接口分离原则（Interface Segregation Principle，ISP）**

- **定义**：不应该强迫客户依赖于它们不使用的方法。即一个类对另一个类的依赖应该建立在最小的接口上，而不是一个臃肿的接口。
- **意义**：避免接口的过度耦合，使接口更加清晰和易于理解。
- **实现方式**：将接口拆分为多个小的、功能单一的接口，让类只依赖于它需要的接口。



以鸟、鱼、兔子为例，说明接口分离原则：

---

## 反例：一个"动物能力"大接口

```java
// 所有动物能力塞在一起（违反ISP）
public interface IAnimalAbility {
    void fly();      // 飞
    void swim();     // 游泳
    void run();      // 陆地跑
}
```

### 各种动物的被迫实现

```java
// 鸟：只会飞，被迫实现游泳和跑步
public class Bird implements IAnimalAbility {
    @Override
    public void fly() {
        System.out.println("鸟展翅高飞");
    }
    
    @Override
    public void swim() {
        throw new UnsupportedOperationException("鸟不会游泳");
    }
    
    @Override
    public void run() {
        throw new UnsupportedOperationException("鸟不擅长陆地跑");
    }
}

// 鱼：只会游泳，被迫实现飞和跑
public class Fish implements IAnimalAbility {
    @Override
    public void fly() {
        throw new UnsupportedOperationException("鱼不会飞");
    }
    
    @Override
    public void swim() {
        System.out.println("鱼在水中游");
    }
    
    @Override
    public void run() {
        throw new UnsupportedOperationException("鱼没有腿");
    }
}

// 兔子：只会跑，被迫实现飞和游泳
public class Rabbit implements IAnimalAbility {
    @Override
    public void fly() {
        throw new UnsupportedOperationException("兔子不会飞");
    }
    
    @Override
    public void swim() {
        throw new UnsupportedOperationException("兔子怕水");
    }
    
    @Override
    public void run() {
        System.out.println("兔子蹦蹦跳跳");
    }
}
```

**问题**：每种动物被迫实现两个完全用不上的方法，只能抛异常。

---

## 正例：拆分成小接口

```java
// 飞行能力
public interface IFlyable {
    void fly();
}

// 游泳能力
public interface ISwimmable {
    void swim();
}

// 奔跑能力
public interface IRunnable {
    void run();
}
```

### 各取所需

```java
// 鸟：只需要飞
public class Bird implements IFlyable {
    @Override
    public void fly() {
        System.out.println("鸟展翅高飞");
    }
}

// 鱼：只需要游泳
public class Fish implements ISwimmable {
    @Override
    public void swim() {
        System.out.println("鱼在水中游");
    }
}

// 兔子：只需要跑
public class Rabbit implements IRunnable {
    @Override
    public void run() {
        System.out.println("兔子蹦蹦跳跳");
    }
}
```

### 特殊动物：组合多个接口

```java
// 鸭子：会飞也会游泳
public class Duck implements IFlyable, ISwimmable {
    @Override
    public void fly() {
        System.out.println("鸭子低空飞行");
    }
    
    @Override
    public void swim() {
        System.out.println("鸭子划水游泳");
    }
}

// 青蛙：会游泳也会陆地跳（用跑接口）
public class Frog implements ISwimmable, IRunnable {
    @Override
    public void swim() {
        System.out.println("青蛙蛙泳");
    }
    
    @Override
    public void run() {
        System.out.println("青蛙跳跃前进");
    }
}
```

## 对比

|              | 大接口 IAnimalAbility  | 小接口 IFlyable/ISwimmable/IRunnable |
| ------------ | ---------------------- | ------------------------------------ |
| 鸟           | 实现3个方法，2个抛异常 | 只实现1个方法                        |
| 鱼           | 实现3个方法，2个抛异常 | 只实现1个方法                        |
| 兔子         | 实现3个方法，2个抛异常 | 只实现1个方法                        |
| 新增"企鹅"   | 修改大接口或继续抛异常 | 实现 ISwimmable 即可                 |
| 方法调用安全 | 运行时才知是否支持     | 编译期就确定                         |

# 5. **依赖倒置原则（Dependency Inversion Principle，DIP）**

- **定义**：高层模块不应依赖于低层模块，二者都应该依赖于抽象；抽象不应依赖于细节，细节应依赖于抽象。
- **意义**：减少模块之间的耦合，提高系统的灵活性和可维护性。
- **实现方式**：通过接口或抽象类来定义模块之间的交互，而不是直接依赖于具体的实现类。例如，使用依赖注入（Dependency Injection）来实现。



依赖倒置原则（DIP）的核心：**高层模块不应依赖低层模块，两者都应依赖抽象；抽象不应依赖细节，细节应依赖抽象。**

---

## 反例：高层直接依赖低层

### 场景：人开车

```java
// 低层：具体汽车类
public class Benz {
    public void run() {
        System.out.println("奔驰车在跑");
    }
}

// 高层：司机类（直接依赖具体汽车）
public class Driver {
    // 写死了只能开奔驰
    private Benz benz = new Benz();
    
    public void drive() {
        benz.run();
    }
}
```

**问题**：司机只能开奔驰，想换宝马必须修改 `Driver` 类。

```java
// 换宝马？得重写Driver
public class BMW {
    public void run() {
        System.out.println("宝马车在跑");
    }
}

// 被迫修改高层代码
public class Driver {
    private BMW bmw = new BMW();  // 改这里
    // 每换一辆车，Driver都要重新编译
}
```

---

## 正例：依赖倒置

### 引入抽象接口

```java
// 抽象：汽车接口（稳定）
public interface ICar {
    void run();
}

// 抽象：司机接口（稳定）
public interface IDriver {
    void drive(ICar car);  // 依赖抽象，不是具体车
}
```

### 低层实现细节

```java
// 奔驰
public class Benz implements ICar {
    @Override
    public void run() {
        System.out.println("奔驰车在跑");
    }
}

// 宝马
public class BMW implements ICar {
    @Override
    public void run() {
        System.out.println("宝马车在跑");
    }
}

// 电动车
public class Tesla implements ICar {
    @Override
    public void run() {
        System.out.println("特斯拉静音行驶");
    }
}
```

### 高层也依赖抽象

```java
// 司机实现
public class Driver implements IDriver {
    @Override
    public void drive(ICar car) {
        System.out.println("司机开始驾驶");
        car.run();
    }
}
```

### 使用：灵活替换

```java
public class Test {
    public static void main(String[] args) {
        IDriver zhangSan = new Driver();  // 张三这个司机
        
        ICar benz = new Benz();           // 今天开奔驰
        zhangSan.drive(benz);
        
        ICar bmw = new BMW();             // 明天开宝马
        zhangSan.drive(bmw);
        
        ICar tesla = new Tesla();         // 后天换特斯拉
        zhangSan.drive(tesla);
        
        // 新增"自行车"也不用改Driver
        ICar bike = new Bicycle();
        zhangSan.drive(bike);
    }
}
```

---

## 对比

|          | 违反DIP                    | 遵循DIP                            |
| -------- | -------------------------- | ---------------------------------- |
| 依赖关系 | Driver → Benz（高层→低层） | Driver → ICar ← Benz（都指向抽象） |
| 换车成本 | 修改Driver源码             | 新增一个类实现ICar                 |
| 扩展性   | 每加新车种改一处           | 加新车种，Driver不动               |
| 测试难度 | 必须造一辆真奔驰           | 可用MockCar测试                    |

# 6. **迪米特法则（Law of Demeter，LoD）**

- **定义**：一个对象应该对其它对象有尽可能少的了解。也称为最少知识原则（Least Knowledge Principle），即一个对象只与它的直接朋友（如自身、参数、成员变量等）交互，而不与朋友的朋友交互。
- **意义**：降低类之间的耦合度，提高系统的可维护性和可扩展性。
- **实现方式**：尽量减少对象之间的直接交互，通过中间类或接口来间接交互。

迪米特法则（LoD）的核心：**只与直接的朋友通信，不要和陌生人说话。** 即一个对象应尽量少了解其他对象的内部结构。

---

## 反例：违反 LoD 的"链式调用"

### 场景：老师让班长清点学生人数

```java
// 学生
public class Student {
    private String name;
    public String getName() { return name; }
}

// 班长
public class Monitor {
    private List<Student> students = new ArrayList<>();
    
    public List<Student> getStudents() {  // 把内部学生列表暴露出去
        return students;
    }
}

// 老师（高层）
public class Teacher {
    // 老师直接深入班长的内部，去操作学生
    public void command(Monitor monitor) {
        // 违反LoD：Teacher → Monitor → Student（跨了两层）
        List<Student> list = monitor.getStudents();
        System.out.println("班级人数：" + list.size());
        
        // 更严重的违反：老师直接修改班长的学生列表
        list.add(new Student());  // 老师越权操作！
    }
}
```

**问题**：
- 老师不该知道班长内部有 `List<Student>`
- 老师拿到了列表引用，可以随意增删，破坏班长封装
- 如果班长改成用 `Set` 存储，老师代码要跟着改

---

## 正例：只和直接朋友说话

### 班长封装细节，提供高层接口

```java
// 学生（不变）
public class Student {
    private String name;
    public Student(String name) { this.name = name; }
}

// 班长（封装内部结构）
public class Monitor {
    private List<Student> students = new ArrayList<>();
    
    // 不暴露内部List，只提供业务方法
    public int getStudentCount() {
        return students.size();
    }
    
    public void addStudent(Student s) {
        students.add(s);
    }
    
    // 即使内部改成Set，外部不受影响
    // private Set<Student> students;
}

// 老师（只和班长打交道）
public class Teacher {
    public void command(Monitor monitor) {
        // 符合LoD：Teacher → Monitor（只认识班长）
        int count = monitor.getStudentCount();
        System.out.println("班级人数：" + count);
        
        // 想加学生？告诉班长，班长自己处理
        monitor.addStudent(new Student("张三"));
    }
}
```

## 更直观的对比

|              | 违反 LoD                                 | 遵循 LoD                              |
| ------------ | ---------------------------------------- | ------------------------------------- |
| 调用链       | `teacher → monitor.getStudents().size()` | `teacher → monitor.getStudentCount()` |
| 知识范围     | 老师知道班长里有List                     | 老师只知道班长能"报人数"              |
| 封装破坏     | 老师能直接修改学生列表                   | 老师无法触及内部结构                  |
| 内部变更影响 | 班长换Set，老师代码崩                    | 班长随便改，老师无感知                |

# 7. **合成/聚合复用原则（Composite/Aggregate Reuse Principle，CARP）**

- **定义**：尽量使用对象组合/聚合，而不是继承来达到复用的目的。组合/聚合可以让系统更加灵活，可以在运行时动态地改变对象的行为。
- **意义**：避免继承带来的复杂性和脆弱性，同时提高系统的灵活性和可扩展性。
- **实现方式**：通过将一个类的实例作为另一个类的成员变量来实现组合/聚合，而不是通过继承。

这些设计原则并不是孤立的，它们相互关联、相互补充。在实际的面向对象设计中，需要综合运用这些原则来构建高质量的系统。同时，这些原则也不是绝对的，需要根据具体的场景灵活运用。



合成/聚合复用原则（CARP）的核心：**优先使用组合（has-a）或聚合（has-a）关系复用代码，而不是继承（is-a）。**

---

## 反例：滥用继承

### 场景：汽车使用发动机

```java
// 发动机
public class Engine {
    public void start() {
        System.out.println("发动机启动");
    }
    
    public void run() {
        System.out.println("发动机运转");
    }
}

// 汽车"继承"发动机（错误！汽车不是发动机）
public class Car extends Engine {
    // Car is-a Engine？语义荒谬
    // 但代码能跑，所以很多人这么写
}

// 使用
Car car = new Car();
car.start();  // 汽车.start()？其实是发动机启动
car.run();    // 汽车.run()？其实是发动机运转
```

**问题**：
- 语义错误：汽车**不是**发动机，汽车**有**发动机
- 强耦合：发动机改接口，汽车被迫跟着改
- 无法替换：想换电动机？只能重写 `Car`

---

## 正例：使用合成/聚合

### 组合关系（强拥有，同生共灭）

```java
// 发动机接口（抽象，便于替换）
public interface IEngine {
    void start();
    void run();
}

// 汽油发动机
public class GasEngine implements IEngine {
    @Override
    public void start() {
        System.out.println("汽油发动机点火启动");
    }
    
    @Override
    public void run() {
        System.out.println("汽油发动机运转，有尾气");
    }
}

// 电动机
public class ElectricEngine implements IEngine {
    @Override
    public void start() {
        System.out.println("电动机通电启动，静音");
    }
    
    @Override
    public void run() {
        System.out.println("电动机运转，零排放");
    }
}

// 汽车：包含发动机（合成/聚合）
public class Car {
    // Car has-a Engine（组合）
    private IEngine engine;
    
    // 构造注入，创建时确定发动机类型
    public Car(IEngine engine) {
        this.engine = engine;
    }
    
    // 也可以Setter注入（聚合，更松散）
    public void setEngine(IEngine engine) {
        this.engine = engine;
    }
    
    public void drive() {
        System.out.println("准备开车");
        engine.start();
        engine.run();
        System.out.println("汽车行驶中");
    }
}
```

### 使用：灵活替换发动机

```java
public class Test {
    public static void main(String[] args) {
        // 汽油车
        Car gasCar = new Car(new GasEngine());
        gasCar.drive();
        
        // 电动车：同一套Car代码，换发动机即可
        Car electricCar = new Car(new ElectricEngine());
        electricCar.drive();
        
        // 甚至运行时换发动机（聚合特性）
        Car hybridCar = new Car(new GasEngine());
        hybridCar.drive();
        System.out.println("---到达服务区，换电池---");
        hybridCar.setEngine(new ElectricEngine());  // 换发动机
        hybridCar.drive();
    }
}
```

## 合成 vs 聚合 的区别

|          | 合成（Composition）            | 聚合（Aggregation）      |
| -------- | ------------------------------ | ------------------------ |
| 关系强度 | 强（整体不存在，部分也不存在） | 弱（部分可以独立存在）   |
| 生命周期 | 同生共灭                       | 部分可提前创建，可复用   |
| 代码体现 | 在构造方法中创建               | 通过Setter或构造传入     |
| 例子     | 人合成心脏（没心脏人活不了）   | 汽车聚合轮胎（轮胎可换） |

```java
// 合成：人合成心脏
public class Person {
    private Heart heart = new Heart();  // 构造时创建，不可换
}

// 聚合：汽车聚合轮胎
public class Car {
    private Tire tire;
    public void setTire(Tire tire) {    // 可以换轮胎
        this.tire = tire;
    }
}
```

## 继承 vs 合成/聚合 对比

|          | 继承（is-a）         | 合成/聚合（has-a）   |
| -------- | -------------------- | -------------------- |
| 耦合度   | 高（父子强绑定）     | 低（通过接口交互）   |
| 灵活性   | 编译期确定，不可换   | 运行期可替换         |
| 复用范围 | 单继承，受限         | 多组合，自由         |
| 语义要求 | 必须是真正的"是一种" | 只要是"有一个"       |
| 修改影响 | 父类改，子类可能崩   | 内部实现改，外部无感 |
